# 人に分かりやすいGUIのレビュー

利用者が作業を正しく完了できるか、どこで迷い・探索・記憶・誤操作の負担が生じるかを評価する。成果物は、問題の根拠、利用者への影響、改善の方向性と優先度である。個別アプリの配置や好みを普遍的なルールにしない。

ブラウザとデスクトップの両方を対象とし、特定のフレームワークを評価の前提にしない。HTMLモックの単一ファイル・オフラインという標準を、本番アプリの構成要件として評価しない。

## 範囲を守る

対象の画面・作業、評価する深さ、求められた報告形式を確認する。レビュー依頼だけでは、対象ファイルの変更、モック作成、実装、コミットを行わない。レビュー結果の文書保存も依頼に含まれる範囲で行う。

改善案の具体的な画面構成、HTMLモック、実装まで依頼されている場合は、その段階に利用可能な `human-friendly-gui-design` を使う。設計スキルがなくてもレビュー自体は完了できる。レビューから設計へ進むためだけに新たな成果物を作ったり、承認済みの作業について再承認を求めたりしない。

明示された要件・確認手順・報告範囲を、一般原則で上書きしない。必要な情報が会話や資料から分かる場合は推定して進め、重要な判断ができない場合にその点を確認する。

## 評価の6原則

正しい作業の完了と誤操作防止、状況と操作の理解、作業効率、見た目の調整の順で評価する。アクセシビリティは各段階の前提とする。

| 原則 | 評価する問い |
|---|---|
| 操作導線の明確化 | 現在位置・対象・次の行動が分かるか。作業順序と配置が合い、不要な往復がないか |
| 情報の適切な圧縮 | 判断材料と操作を保ったまま整理できているか。比較・確認に必要な情報を同時に見渡せるか |
| アフォーダンスの明確化 | 操作できる要素を見分けられ、ラベルから対象・意味・結果を予測できるか |
| 冗長性の排除 | 重複や装飾が作業を圧迫していないか。整理案によって操作・状態・復帰経路を失わないか |
| 認知負荷の低減 | 用語や配置が一貫し、記憶で補わず判断できるか。作業の文脈が保持されるか |
| 予測可能性と利用者の制御 | 状態変化と結果の適用範囲を理解できるか。誤操作を防ぎ、必要な修正・中断・復帰ができるか |

情報を少なくすること、主操作を1つにすること、カード化することなどを自動的な改善案にしない。作業目的・使用頻度・判断材料・誤操作の影響から評価する。認知・知覚の原則から普遍的な件数や寸法を導かない。

ブラウザやOSなど対象の実行環境の慣習と既存の部品・デザインシステムを踏まえる。利用者が習得した操作の変更には理由が必要であり、新しい外観だけを改善の根拠にしない。

## レビューの進め方

### 作業と現状を把握する

代表的な作業、利用者、使用頻度、判断材料を必要な範囲で整理する。既存画面では、可能なら表示と操作を確認し、必要なコードや既存テストから機能・状態・操作経路を把握する。対象ファイルや利用者データに変更を加える操作は、レビュー依頼だけで実行しない。

表示上の要素が操作・選択・状態・ナビゲーションを兼ねる可能性を確認する。スクリーンショットしかない場合は、動作を断定しない。HTMLモックの模擬動作から、実アプリの動作を確認済みと扱わない。

### 問題を診断する

[レビュー観点](references/review-checklist.md)を読み、依頼に関係する作業と状態を選んで確認する。表面的な好みではなく、具体的な状況と利用者への影響を結び付ける。問題がなければ、指摘を作るために作らない。

既存画面を整理する提案では、機能、操作経路、比較できる範囲、判断に必要な状態、文脈保持への影響を確認する。より適切な表現に変えることと、機能を削ることを区別する。

### 優先度と方向性を示す

作業を妨げる問題、負担を増やす問題、見た目の調整を分ける。「重大な問題だけ」などの指定がある場合は、その範囲で報告する。

各指摘は、対象箇所、状況、利用者への影響、改善の方向性を示す。複数案があれば、作業への影響と推奨を示す。詳細なモック制作や実装はレビューの完了条件にしない。

最後に確認した範囲と未検証部分を簡潔に伝える。依頼にない全体改修、テスト追加、他エージェントによる再レビューへ広げない。
