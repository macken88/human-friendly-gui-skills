# 作業を通したGUIレビュー

チェック項目の数を満たすことより、利用者が作業を正しく完了できるかを確かめる。依頼の目的と変更範囲に関係する観点を選ぶ。

## 確認の観点

| 観点 | 確認すること |
|---|---|
| 導線 | 現在位置、操作対象、次の行動、結果が分かるか。不要な往復がないか |
| 情報構造 | 関連する情報がまとまり、比較・確認に必要な値が同時に見えるか |
| 開示 | 隠した情報や操作に必要な場面で到達できるか。利用者の記憶で補わせていないか |
| 操作の見分け | 操作要素を見分けられ、ラベルから対象と結果を予測できるか |
| 冗長性 | 説明、装飾、操作の重複が作業を圧迫していないか。削除で役割を失っていないか |
| 状態 | 選択、適用条件、未保存、処理中、完了、失敗を理解できるか |
| 制御と復帰 | 意図しない変更を防ぎ、必要な修正・中断・取り消しができるか |
| 文脈保持 | 更新や画面切替で入力、選択、条件、作業位置が失われないか |
| アクセシビリティ | キーボード、フォーカス、ラベル、配色、状態表示が作業を支えるか |
| 制約への対応 | 縮小、長い文言、大量データ、空やエラーで重要な情報・操作を失わないか |

既存画面の改善では、変更前後で代表的な機能と操作経路を対応付ける。クリック、タップ、キーボード、ショートカット、右クリック、複数選択、直接編集など、対象で利用され、変更の影響を受ける経路を確認する。見た目だけで操作要素を情報要素と判断しない。

## 実行環境に応じた確認

次は共通原則を実際の操作に当てはめるための観点であり、すべてのGUIへの必須要件ではない。対象の環境、利用者の作業、変更範囲に関係するものを選ぶ。未対応の環境への対応追加を、レビューだけで要求しない。

| 適用する場面 | 確認すること |
|---|---|
| キーボードで操作する画面 | フォーカス順と表示が作業に合うか。ダイアログなどを閉じた後、適切な対象へ戻るか。独自ショートカットがブラウザやOSの標準操作を妨げないか |
| 未保存の入力や編集がある画面 | 遷移・終了時のデータ損失を防げるか。保持・復元・警告などを影響に応じて選び、不要な確認を重ねないか |
| ブラウザ内で画面を移動する作業 | 戻る・進む、再読み込みで予測できる画面と状態になるか。継続に必要な入力、選択、条件、作業位置の扱いが明確か |
| URLで共有・再訪する画面や検索結果 | 直接URLを開いて目的の対象へ到達できるか。共有に必要な条件が復元されるか。機密情報や一時的な入力まで一律にURLへ載せないか |
| Web技術で作る操作要素 | 動作にはボタン、移動にはリンクなど意味の合う要素を使うか。リンクを利用者が別タブで開く標準操作を妨げないか。名前・役割・状態が支援技術に伝わるか |
| タッチ端末を想定する画面 | ホバー・右クリック・ドラッグだけに必要な操作を委ねていないか。タップで操作を見つけて完了できるか |
| 画面幅や文字サイズが変わる利用 | 狭い表示幅、ウィンドウの縮小、ブラウザの拡大表示でも、必要な情報と操作に到達できるか。比較に必要な関係を保ち、意図しない重なりや欠落を防げるか |
| 通信・時間のかかる処理がある画面 | 読み込み中、データなし、失敗、権限不足など関連する状態を区別できるか。再試行時に入力を失わず、意図しない重複実行を防げるか。状態変化が視覚と必要な読み上げに伝わるか |
| デスクトップのウィンドウやOS連携 | ウィンドウの切替・終了、メニュー、ショートカットなどが対象OSの慣習に合い、作業対象や未保存状態を取り違えないか |

## 確認方法

表示の確認と動作の確認を分ける。

- 表示: 情報の優先順位、整列、文言、状態の区別、操作領域、画面全体の面積配分を見る。
- 動作: 代表的な作業を実際の入力経路で操作し、対象・設定・結果が意図どおりかを見る。
- 既存テスト: 変更した作業の確認に使えるものを活用する。表示を見ただけで動作確認の代わりにしない。

未選択、処理中、エラー、長い文言などは、当該画面で起こり得て判断に影響するものを選ぶ。すべての状態や画面を毎回網羅する必要はない。

## 指摘の扱い

- **作業を妨げる問題**: 必要な操作ができない、対象を取り違える、入力や結果を失う、結果を誤認するなど。優先して扱う。
- **負担を増やす問題**: 頻繁な操作を見つけにくい、比較に記憶が必要、不要な往復や手数が増えるなど。作業への影響を示す。
- **見た目の調整**: 完了や判断への影響が小さい細部。依頼に合わせて扱う。

「重大な問題だけ」など、利用者が指定した報告範囲を守る。認知原則の名称や好みだけを指摘の根拠にしない。

## 報告

必要な指摘について、状況、利用者への影響、改善案を結び付ける。意図的な機能変更と、意図しない欠落を区別する。

判断を求める場合は、具体的な状況、用語の意味、選択肢の影響、推奨を示す。HTMLモック、実アプリの操作、コード、テストのどこまで確認したかを伝え、未検証部分を明示する。
