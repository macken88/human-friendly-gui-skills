# HTMLモックの作り方

画面の構成、情報の見せ方、操作導線、状態変化を利用者が確認できるHTML文書を作る。実アプリを完成させることは、この手順の目的に含めない。

## 出力場所と形式

- 利用者が指定した場所・形式を優先する。未指定なら適用先リポジトリの既存の文書配置に合わせる。慣習がなければ `mockups/<題材>.html` とする。
- 他のリポジトリでスキルを使う場合、モックはその利用先へ出力する。スキル配布用の `human-friendly-gui-skills/mockups/` へ戻して出力しない。このリポジトリ自体が作業対象の場合は、ここの `mockups/` を使える。
- 標準はCSSと必要なJavaScriptを内包した単一HTMLとし、オフラインで開けるようにする。既存環境や利用者の指定があれば、それに合わせる。
- 不要な依存、ビルド手順、外部通信、実データへの書込みを追加しない。入力データは架空または利用を認められたものを使い、個人情報や秘密情報を持ち込まない。
- 既存文書を置き換える場合は、元の用途と内容を確認する。出力物を勝手にGit管理外にしない。

単一HTML・オフラインという標準と依存を抑える方針は、確認用モックのためのもの。本番のブラウザ・デスクトップアプリのフレームワーク、ファイル構成、ビルド、バックエンド通信を制約しない。

## 文書の構成

題材に必要な内容を選び、重複説明を避ける。次は固定の章立てではなく、確認に必要な情報である。

| 内容 | 示すこと |
|---|---|
| 目的と対象作業 | 誰が、何を判断・操作する画面か |
| 代表シナリオ | 開始状態、主要な操作、その結果 |
| 画面案 | 実際に使う文言と現実的な量・長さのデータ |
| 関連状態 | 未選択、空、処理中、完了、失敗など、作業に関係するもの |
| 設計理由 | どの負担をどう減らし、何を保全するか |
| 確認事項 | 判断が必要な箇所、選択肢の影響、推奨 |
| 確認の範囲 | HTMLで再現したものと、実アプリで検証するもの |

文書の目次、画面案、設計理由、確認事項を直接リンクでつなぐ。確認事項は関連する画面や要素を特定し、文書内を探し回らずに判断できるようにする。設計注記はアプリ画面の外に置き、利用者向けUIへ混ぜない。

## 操作の再現

導線の確認に必要な範囲で、画面遷移、選択、詳細開閉、入力、状態切替を再現する。静的な配置確認だけで十分なら、不要な操作を作らない。

再現する操作には `button`、`a`、`label`、`input` など意味の合う標準要素を使う。キーボードで到達・操作でき、フォーカスが分かるようにする。

状態切替や検証用の操作は、模擬アプリの操作と区別する。実処理を行わない箇所は、その限界を文書で明示する。「保存」「削除」「実行」を模擬する場合は、模擬であることが操作時にも分かるようにする。

HTMLで再現する状態変化は、ラベルの意味と一致させる。処理開始、中断、完了などの違いが設計判断に関係する場合、単に完了メッセージを出すだけで済ませない。

## 出力後の確認

可能ならブラウザで開き、目次や確認事項のリンク、必要な操作、関連状態を確認する。代表的な画面サイズに加え、縮小時と長い文言で作業が妨げられないかを必要な範囲で見る。

テーマや文字サイズを複数扱う場合は、状態の区別と読みやすさも確認する。HTMLの見た目が整っていても、実アプリの描画・ショートカット・処理・状態保持を検証したことにはしない。

ブラウザ確認ができなければ、リンクや構造を確認した範囲と、表示・操作が未検証であることを報告する。
