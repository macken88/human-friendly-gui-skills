# 作業に合うテンプレートを選ぶ

HTMLテンプレートは画面構成と操作の出発点であり、完成したアプリや必須のデザインシステムではない。既存画面の小さな修正には、テンプレートを適用せず必要な変更だけを行える。

## 選択の基準

アプリの業種やフレームワークではなく、その画面の主要な作業と完了条件から選ぶ。一つのアプリに複数の型を組み合わせられる。ホームとサイドパネルの選択は[アプリ全体の導線](app-navigation.md)を読む。

| 型と原本 | 適する作業・完了条件 | 別の型を選ぶ場面 | 保持する文脈・組み合わせ |
|---|---|---|---|
| [検索・一覧・詳細](../assets/templates/screens/search-detail.html) | 対象を探して選び、必要な詳細や対象操作へ到達する | 可視化から関係を調べるなら探索、同種対象を順に処理するなら逐次確認 | 検索条件、選択、一覧位置。詳細にフォームや編集領域を組み合わせる |
| [入力・設定・確認](../assets/templates/screens/form-confirmation.html) | 項目を入力し、対象と適用内容を理解して確定する | 順序のないキャンバス・文書編集はワークスペース | 入力、検証結果、未保存状態、適用対象。確認段階は影響に応じて省略できる |
| [取り込み・対応付け・検証](../assets/templates/screens/import-validation.html) | 外部データを確認・対応付け・修正し、取り込み内容を確定する | 単なるファイル選択や1件の貼付けは他の型の部品にする | 元データ、列対応、問題行、確定範囲。問題時に全件停止するか部分取込するかは用途で決める |
| [実行・ジョブ管理](../assets/templates/screens/job-management.html) | 条件に基づいて処理を投入し、終了や失敗と結果を追跡する | 短い処理で管理作業がなければボタンと状態表示で足りる | 条件、対象、ジョブ識別、進行状態、結果。フォームから実行し探索・比較へつなぐ |
| [可視化・分析・探索](../assets/templates/screens/visual-exploration.html) | 条件を変え、関係・傾向・異常を理解する | 特定レコードへの到達が主目的なら検索、候補を選ぶなら比較 | 対象、条件、表示範囲、注目点、指標の意味。一覧や比較と組み合わせる |
| [比較・選定・採否判断](../assets/templates/screens/comparison-selection.html) | 候補間の違いを理解し、選定・採否を決める | 1件ずつ独立に処置するなら逐次確認 | 候補、共通条件、差分、判断根拠。指標の良し悪しと比較可能性を明示する |
| [逐次確認・処置](../assets/templates/screens/sequential-review.html) | 同種の対象へ判断・修正・保留を繰り返し、未完了を把握する | 複数候補を並べて選ぶなら比較 | 現在位置、判定、未完了、直前操作。撮影・アノテーションでは取得や編集領域を加える |
| [制作・編集ワークスペース](../assets/templates/screens/editing-workspace.html) | 成果物を自由な順序で編集し、変更を保存する | 項目を埋めることが中心ならフォーム | 編集内容、選択、履歴、未保存状態、表示範囲。プロパティ欄へフォームを組み合わせる |

取り込みには[設定画面付きの派生](../assets/templates/screens/import-settings.html)も用意する。ファイル選択だけで条件が決まるなら同一画面、文字コード・区切り・シート・列対応などを確認する段階が必要なら設定画面付きから始める。単純な取り込みを理由なく多段階にしない。

実行・ジョブ管理はカード／表、比較・選定は一覧と専用比較画面／同一画面をモック内で比較できる。すべての画面に複数のスタイルを用意する必要はない。構成、実行方式、操作、レスポンシブ表示の選択は[表示・操作・実行方式](interaction-patterns.md)を参照する。

画面を「対象は何か」「繰り返す操作は何か」「何をもって完了か」で説明する。複数の型に当てはまる場合は主な作業を中心にし、必要な部品を組み合わせる。画像、表、グラフを使っているという理由だけで型を決めない。

## 原本から確認用モックを作る

1. 選んだ原本だけを読み、依頼先の出力場所へコピーして適応する。スキル配布用の原本を個別案件のデータで上書きしない。
2. 架空例の題材・項目・文言・件数・状態・完了条件を、対象作業に置き換える。原本の候補数、CSVの列数、処理時間、必須入力、確認段階を普遍的な要件にしない。
3. [HTMLモックの作り方](html-mockups.md)に従い、設計理由と確認事項を模擬アプリの外に置く。テンプレートの検証操作も本番UIへ混ぜない。
4. 必要な操作と関連状態を確認する。HTMLで確認できない実処理、保存、中断、権限、再読み込み後の復元は、実装で別途検証する。

各原本はCSSとJavaScriptを内包し、通信や外部ライブラリなしで単独動作する。状態はページ内のメモリだけにあり、再読み込みで初期化する。青緑・青・グレーのスタイルと明暗配色は、開いたまま切り替えられる。色の選択で操作結果や判断状態を変えない。移植先の既存スタイルや実装技術を優先する。

空・読み込み中・エラーの検証切替は画面全体の状態例で、各作業に必要な詳細なエラー処理の代わりにはならない。フォーム、取り込み、ジョブなどには作業固有の状態も用意している。

状況把握・対応のダッシュボードは、このスキルのテンプレート対象に含めない。必要になった場合は作業目的から個別設計する。AI補助、ログイン、履歴、出力なども今回の独立テンプレートには含めず、対象作業に必要な部品として扱う。
